# Relational Tables Phase 1: What Actually Renders, and What Only Passes Tests

Notes from Task 6 of the relational-tables phase (demo content, four folded-in
fixes, a live-image look at the whole thing, and a fix round after the first
pass at that look reached the wrong conclusion). Everything numeric below was
measured directly, either against the running GT image via `bin/gt-eval` or
against the same headless CLI eval `test/run-pharo-tests.sh` itself uses, not
copied from an earlier report — where a number here differs slightly from an
earlier task's report, that is because it is a fresh measurement, not a typo.
This note's first version misdiagnosed the central defect; that version is
preserved in git history, and this one names the mistake rather than quietly
replacing it, since the wrong turn is as much a lesson as the right answer.

## `beReplace` adornments do not compose, and the failure mode is not a clean nest

Applying two `beReplace` adornments where one's source range is a subset of
the other's does not produce a nested widget. It splits the outer attribute's
run into pieces, and the pieces do not all render the same way. Measured
directly: text `'ABCDEFGHIJ'`, one adornment (a 40x20 red box) applied
`from: 2 to: 9`, a second (a 20x20 blue box) applied `from: 4 to: 6`, both
`beReplace`, in an otherwise-plain `BrEditorElement`. The render was not "red
box containing a blue box." It was: literal characters `A`, `B`, `C` (the
first split piece of the outer run, positions 2-3, rendered as plain text —
not a widget, not the outer's box, just inert characters); then the blue box
alone (positions 4-6, the inner adornment, which did win at the exact
overlap); then the red box alone (positions 7-9, the outer's second split
piece, which still rendered as a widget); then literal `J`. Reproduced twice
with fresh objects each time and got the same layout both times, so within
this construction it is deterministic, not a race — but it is a genuinely
different failure shape than "the inner slot shows a copy of the outer,"
which is how the original checkbox-in-a-table defect was described. Take the
one actionable fact from this, not the exact shape: **overlapping `beReplace`
ranges are unsupported and the visible result is unpredictable enough that
"exactly one adornment may cover a given range" has to be an invariant the
code maintains itself** (which is exactly what `visitTable:` does now — a
cell's markup is styled on the cell's own fresh rope via
`McMarkdownInlineStyler`, never by re-running a pass over the outer
document's rope inside a range something else already replaced). Do not rely
on `beReplace` nesting to do anything predictable, and do not "fix" a nesting
bug by trying to make the overlap render correctly — remove the overlap.

## The real defect: a checkbox in a cell blinds Microdown to any emphasis after it — not an embedded-editor realization problem

**This section corrects a wrong diagnosis this note originally shipped with.**
The first pass at this investigation found that the demo table's emphasis
cells rendered raw, uncollapsed markdown in the live window, framed it as
"a bare embedded `BrEditorElement` only reliably shows hidden delimiters and
font-weight styling when it is the only editor in its `BlSpace`," and
reported that as the root cause with the fix deferred as out-of-scope future
work. That framing was wrong, caught on review, and worth recording exactly
*how* it was wrong, because the evidence really did point that way until one
more experiment ruled it out.

**The reframe that broke the false lead:** put a cell containing *both* a
checkbox and bold text — `'[ ] **fig**'` — in a one-row table, standalone,
the *only* editor in its space. If the "ordering"/"multiple editors" theory
were right, this should render fine (one editor, first and only). It did
not: checkbox rendered, `**fig**` stayed raw. So multiplicity of editors was
never the variable — the previous investigation's two-cell tests just
happened to pair a working construction (`'**fig**'` alone) with a
non-working one (`'*bar*'`, single-asterisk italic — see below) and mistook
the difference for position.

**The actual cause, found by checking what `MicInlineParser` — Microdown's
own inline parser, not this project's code — does with the cell's source
directly:** `MicInlineParser new parse: '[ ] **fig**'` answers exactly one
`MicTextBlock` and no `MicBoldFormatBlock` at all. `'x **fig**'` parses fine
(`MicTextBlock`, `MicBoldFormatBlock`); `'[x] **fig**'`, `'[foo] **fig**'`,
and even `'[ ] x'` alone all collapse to a single opaque `MicTextBlock`,
while `'(x) **fig**'` and `'] **fig**'` (an unmatched *close* bracket) do
not. The pattern is exactly what CommonMark link-parsing looks like from the
outside: an unresolved `[` reads as the start of a link, and once the parser
cannot complete one, it swallows the rest of the line into one literal text
run — hiding every emphasis node after it, including ones that have nothing
to do with the bracket. `styleCheckboxes`, `styleColours` and `styleButtons`
never hit this because they scan `source` with a plain regex; `styleEmphasis`
is the one styling method that hands `source` to `MicInlineParser`, so it is
the only one that goes blind.

**The fix** (`pharo/McMarkdownInline.st`, `styleEmphasis` /
`maskedForEmphasis`): before parsing, replace `[ ]`/`[x]`/`[X]` in a copy of
`source` with same-length spaces (the identical regex `styleCheckboxes`
already uses), and parse *that* instead of the raw source. The mask is
character-for-character the same length as what it replaces, so every
`start`/`end` `MicInlineParser` reports still indexes correctly into the
real, unmasked `source` — nothing downstream of `styleEmphasis` needed to
change. Confirmed: `MicInlineParser new parse: '    **fig**'` (checkbox
masked to four spaces) answers `MicBoldFormatBlock` with `start`/`end` of 5
and 11 — exactly where `**fig**` sits in the *original*, unmasked
`'[ ] **fig**'` too, since masking preserved length and position exactly.

**A second, independent defect this same investigation turned up in the demo
content, not the styler:** `MicInlineParser new parse: '*bar*'` — no
checkbox anywhere — also answers a single `MicTextBlock`, no
`MicItalicFormatBlock`. Tried `'x *bar*'`, `'*sort the rows*'`,
`'x *sort the rows*'`, `'*a*'`/`'*ab*'`/`'*abc*'`: none of them parse as
italic. `_bar_`, `'x _bar_'` and `'some _italic_ text'` all parse correctly
to `MicItalicFormatBlock`. **This Microdown build does not recognise
single-asterisk italic (`*text*`) as emphasis at all — only underscore
(`_text_`).** (`__bar__`, for the curious, parses as two independent
`MicItalicFormatBlock`s, not one bold — double-underscore is not this
parser's bold spelling either; only `**` is.) Every italic test already in
this suite already used underscore (`testItalicOffsets`,
`testItalicHidesDelimitersWhenCursorAway`, `testFragmentStylesItalic`), which
is exactly why nobody had hit this before: the one place asterisk-italic got
used was the new demo table cell. Fixed by writing the cell as
`_sort the rows_` instead of `*sort the rows*` — matching the convention the
original `demoContent` paragraph already used ("some _italic_") — not by
teaching the styler a new syntax.

**What chasing the false lead was still worth learning**, since it is real
GT/Bloc behaviour even though it was not this bug:

- **`BrEditor` needs an aptitude to render *anything***, not just to look
  right. `BrEditor new; text: 'plain text' asRopedText; styler: (a working
  BlPluggableStyler)`, added to a shown `BlSpace`, rendered a *blank* page —
  the styler's own attribute changes never appeared because there was
  nothing else visible to show them on. Adding
  `aptitude: BrGlamorousRegularEditorAptitude new` before `text:` fixed it:
  base text appeared *and* the styler-applied `BlTextForegroundAttribute`
  correctly coloured it. `BrEditorElement` (what the cells actually use) has
  no such requirement — it renders plain text with no aptitude at all, which
  is exactly why the cells were never blank, only unstyled.
- **`BrEditor inheritsFrom: BrEditorElement`, not the reverse** — `BrEditor`
  is the richer subclass (it alone understands `#styler:`) and is what
  `McRichEdit`'s own top-level editor is built from; `editorElementFor:`
  deliberately uses the cheaper `BrEditorElement` for cells. Swapping a
  cell's `BrEditorElement` for a `BrEditor` (with aptitude and a
  `BlPluggableStyler` re-running the same styling `cellTextFor:isHeader:`
  already does) *did* make `'[ ] **fig**'` render correctly bold — but so did
  leaving the cheap `BrEditorElement` in place once `styleEmphasis` itself
  was fixed, and the `BrEditor` version was measurably worse engineering (a
  second, redundant styling pass per keystroke-equivalent render, and one
  path where it briefly rendered *nothing* while this was being worked out).
  Chased far enough to be sure it was a dead end, not stopped early.
- **Comparing the extents of a `BrEditorElement` against a bare
  `BlTextElement` for the same source is not a reliable regression signal.**
  `'[ ] **fig**'` styled correctly (`BrEditorElement`, checkbox collapsed
  delimiters) measured 69.60px; the identical *source* as a plain, padded,
  unstyled `BlTextElement` (no checkbox widget, no styling at all) measured
  71.11px — only a 1.5px gap, because the two element classes carry
  different intrinsic overhead unrelated to content. The same styled cell
  compared against *itself* with only `BrTextHideAttribute` and
  `BlFontWeightAttribute` stripped (same checkbox widget, same base text,
  same `BrEditorElement`, via `aRopedText copy;
  clearAttributesOfClass: BrTextHideAttribute; clearAttributesOfClass:
  BlFontWeightAttribute`) measured 103.20px against the styled version's
  69.60px — a 33px gap, matching independently-measured
  delimiter-collapse savings almost exactly, and reliably reproduces the
  original bug's *exact* width (103.20px) when `styleEmphasis`'s fix is
  reverted. Compare a styled element against a same-class, same-content,
  selectively-de-attributed copy of itself, not against a different element
  class built from the literal source — the latter's noise floor swamps the
  signal.

## `BrTextHideAttribute` and `BrTextAdornmentDynamicAttribute` are siblings, both under `BrTextAdornmentAttribute`

Confirmed directly: `BrTextHideAttribute superclass` and
`BrTextAdornmentDynamicAttribute superclass` both answer
`BrTextAdornmentAttribute`. An `isKindOf: BrTextAdornmentAttribute` check
(used by `hasAdornment:` to decide cheap-element-vs-editor) is correct for
that decision — it should count a hide attribute as needing the editor — but
the same check would over-count if used anywhere that means "how many
interactive widgets does this cell have," since it would also match every
collapsed emphasis delimiter. The narrower
`isKindOf: BrTextAdornmentDynamicAttribute` (used everywhere the code
actually counts widgets, e.g. the table-nesting regression test) is the
one that means "widget," not "adornment of any kind."

## Reading a live `BrTextEditorModel`'s `text` requires the UI process — not just moving the cursor

The brief already knew `navigator moveTo:; apply` needs the UI thread. What
is not obvious going in: a plain **getter**, `model text`, raises the same
`I am running from a non-UI process` error from a `gt-eval` script, for any
`BrTextEditorModel` that is actually attached to a shown space — the demo's
top-level editor and a table cell's embedded editor both hit it. So there is
no way to read back the live document's current text, or drive
`McRichEdit>>replaceFrom:to:with:` (which calls exactly that getter), from
outside the UI process. To confirm a document mutation (e.g. that clicking a
sort header actually rewrites the rows), build the same
reader/relation/element objects the running code would build, drive the
mutation through the object graph directly (`McMarkdownTableReader
>> sortEditBy:ascending:`, or a `McRecordingOwner` the way the unit tests
already do), and render the *result* in a fresh, separate `BlSpace` — the
same "separate render" trick the brief already prescribes for the
cursor-near case, generalized to any live-mutation check.

## `gt-eval` scripting: a `Smalltalk at:#Foo put:` binding is unusable as a bare identifier in the same script

Task 5 already found this for class definitions; it is not special to
classes. `Smalltalk at: #Foo put: aValue. Foo someMessage` fails with
`Undeclared variable` in a single `gt-eval` script — the global exists (`(Smalltalk at:
#Foo)` resolves fine on the very next line), but the *compiler* for that
script's later statements does not see the binding created by an earlier
statement's *execution*, only what existed when the whole script was parsed.
Always refer back to it as `(Smalltalk at: #Foo)`, not bare `Foo`, anywhere
later in the same script.

## SUnit can assert on a real render: `BlSpace`/`pulse`/`exportAsForm` work headlessly in `test/run-pharo-tests.sh`'s own CLI eval, not only against the running GUI app

Everything above about a render being needed came from `bin/gt-eval` against
an already-running, windowed GT app. It is natural to assume that means
render-based assertions can only happen there, outside SUnit. Not so:
`test/run-pharo-tests.sh` invokes `GlamorousToolkit-cli … eval "…"` — a
separate, non-windowed process — and inside that exact invocation,
`BlSpace new; extent: …; show. space pulse. space root exportAsForm` runs
and returns a real, non-zero `Form` with correctly measured child extents
(confirmed: a bare `BlTextElement` inside such a space measured
`39.3@15.0`, matching what the same construction measures against the live
GUI app). So a regression test can build a real element, add it to a real
(if invisible) `BlSpace`, `pulse` it, and assert on the resulting `extent` —
which is exactly what closes the gap this whole investigation is about:
attributes-only tests cannot see a rendering defect, but an extent assertion
against a `pulse`d `BlSpace` can. `space close` afterward to tidy up. This
same CLI eval is subject to the "`Smalltalk at:put:` then bare identifier"
restriction above — reference project classes as `(Smalltalk at:
#McRelation)` etc. when fileIn-ing them in the same script, exactly as
`test/run-pharo-tests.sh` already does for its own test-suite classes.

`BlRunRopedText >> clearAttributesOfClass:` (discovered via
`allSelectors select: [...substring...]`, since it is not otherwise
documented anywhere in this project) removes every attribute of a given
class from a text without touching anything else — used to build a
same-class, same-content, selectively-de-attributed comparator for the
extent test above (see "Compare a styled element against a same-class...").

## Cropping an exported `Form` is worth doing for anything with small detail

`space root exportAsForm` followed by `form copy: (x@y corner: x2@y2)` before
`PNGReadWriter putForm:onFileNamed:` produces a zoomed-in PNG of just the
region under inspection (e.g. just the table), which made the difference
between "the arrow glyph might be there" and actually reading whether an
adornment collapsed or not at native screenshot resolution.
