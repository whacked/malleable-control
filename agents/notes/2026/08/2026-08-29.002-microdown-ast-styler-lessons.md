# Microdown as a Projection Parser: What It Does and Does Not Give You

Notes from replacing McRichEdit's regex scanners with a Microdown parse → AST →
BlText styling pipeline. Microdown is already in the GT image (packages
`Microdown`, `Microdown-RichTextComposer`, …), so nothing had to be loaded. The
parser class is **`MicrodownParser`**, not `MicParser`, and the visitor base is
**`MicrodownVisitor`**.

## Blocks carry no source offsets; inline nodes do

This is the single fact the whole design turns on.

`MicAbstractBlock` has exactly four instance variables — `parent`, `properties`,
`children`, `parser`. There is no `start`, `stop`, `interval` or
`sourceInterval`. A block cannot tell you where in the document it came from,
which is precisely what a projectional editor needs.

Inline nodes are the opposite: `MicBoldFormatBlock` and friends have `start`,
`end` and `substring`, and `start`/`end` span the **raw** run including the
delimiters (`**bold**`, not `bold`). Those offsets are relative to the string
that was inline-parsed, not to the document.

So block ranges have to be reconstructed. `MicrodownParser >> parse:` is a
plain line loop over `handleLine:`, which makes it cheap to drive that loop
yourself and stamp ranges as lines are consumed. Two rules cover every block
Microdown builds:

1. a node that did not exist before a line was handled was created by it, so
   its range starts on that line;
2. a node still open — on the path from `current` up to the root — consumed the
   line, so its range extends to it.

## Microdown joins a block's lines with CR before inline parsing

A two-line paragraph's `text` is the lines concatenated with a single
`Character cr` between them, so inline offsets past the first line are shifted
by one relative to the document, and by more once a markup prefix (`> `, `#`,
`- `) is stripped from each line.

Aligning the inline string against the source by searching for substrings gets
the first line right and then silently drifts — the bold run comes back one
character to the left, which looks like an off-by-one in the styler and is
not. The fix is to build the inline string and its index map together, one
line at a time, so the mapping is recorded rather than inferred.

## `text` means different things on different blocks

- `MicParagraphBlock >> text` and `MicQuoteBlock >> text` answer the **raw**
  source, delimiters included.
- `MicHeaderBlock >> text` and `MicListItemBlock >> text` answer the text with
  the inline delimiters already **stripped**.

So `text` cannot be used as "the string the inline offsets refer to". Rebuild
it from the document instead, per block class, stripping the block markup.

## The GFM table separator row is handled two different ways

`MicTableBlock >> isHeader:` accepts a line made only of `|`, `-` and spaces.
That means:

- `|---|---|` is recognised, dropped from `rows`, and sets `hasHeader` to true;
- `|:---|---:|` contains colons, so it is **not** recognised, stays in `rows`
  as if it were data, and leaves `hasHeader` false.

Any table rendering has to handle both, and neither `rows` nor `hasHeader` is
sufficient alone. Column alignment is only available in the second case, since
the first discards the row that carried it.

`isHeader:` also crashes the parser for an incomplete row: it answers true for
a bare `|`, so no row is contributed, and `closeMe` then takes `rows first
size` on an empty collection. Typing the first pipe of a table therefore
raised `SubscriptOutOfBounds`. Patched in `McGtPatches patchMicrodownEmptyTable`.

## Microdown recognises `***` as a horizontal rule, but not `---` or `___`

`---` arrives as a `MicParagraphBlock` whose text is `---`. GFM accepts all
three spellings, so the styler recognises the other two itself rather than
letting them render as literal text.

## `BlTextBackgroundAttribute` applies but paints nothing

It compiles, it lands on the range, `attributesAt:` finds it — and a `BrEditor`
draws no background at all, even with an opaque colour. The attribute GT's own
`BlRunRopedText >> highlight:` produces is **`BlTextUnderlayAttribute`**
(`BlTextUnderlayAttribute paint: aColor`), and that one does paint. Use it for
code-block and inline-code tints.

## Strikethrough parses, but into nonsense

The spec assumed `~~struck~~` was not in Microdown. It is — `MicStrikeFormatBlock`
exists and the parser emits it — but each `~~` becomes its own node with an
empty `substring`, so `a ~~struck~~ z` yields Text/Strike/Text/Strike/Text
rather than one strike wrapping the content. There is nothing to style, so
there is no `visitStrike:`. Strikethrough stays out of scope, for a different
reason than the spec gave.

## Nested list items are dropped

`- one / - two / ␣␣- nested` parses to a list with two items. The indented item
does not appear at all. Nesting was not needed here, but do not assume it.

## Chunk format: a free-floating comment needs its own terminator

`pharo/McRichEdit.st` carried a block of developer-note comments between two
method protocols with no `!` after them. In chunk format that comment runs on
until the next `!` — which is the one **opening** the following protocol
header. The header is then evaluated as an ordinary expression, so the file
fails to load with:

    Message not understood: McRichEdit class >> #methodsFor:

The error points at the first protocol in the file, not at the comment, which
makes it thoroughly misleading. Any chunk between protocols needs its own
trailing `!`. (This joins the known rule that a literal `!` inside a string or
comment must be doubled — the same block also has to avoid writing `!` in
prose.)

## Regression risk worth knowing

`assert:equals:description:` does not exist in this image's SUnit;
`assert:description:` and `assert:equals:` do. And a fresh `McRichEdit new`
used to fail in `palette` because `darkMode` was nil until `openView` ran —
`initialize` now sets it, which is what makes the class testable at all.
